### T?: a merge loop whose body is a 500-instruction register network must stay rolled, the fully unrolled form reaches 20k to 40k SASS instructions per kernel and runs 1.6x to 2.7x slower at one warp with the same instruction mix
applies to: every per-thread loop whose body is a full compare-exchange network on register arrays (W4's chunked merge, the per-chunk sorts of a two-level list, B2 and B6 style per-thread merges, any chunked serial merge with a bitonic or odd-even body), one warp above all, any key width
measured: W4_wmerge (warp truncated merge sort: per-lane Batcher sort of 64 words, then 5 merge-path levels, each lane merging 64 outputs per level in chunks of 16 with a 48-exchange network per chunk), same source except the chunk loop (`#pragma unroll` over the 4 chunks of a level against `#pragma unroll 1`, every register index inside the body a compile-time constant in both) and a tree sum of the 16 win flags instead of a serial add chain. B200 umbriel-b200-091 sm_100, nvcc 13.4.92, 2026-10-25, harness 0.8 chain-slope latency, W2_packed control in the same lock section in both batches: bf16 N 2048 k 1024 59199 against 21783 cycles (2.72x, control 150080 and 150079), fp32 N 2048 k 1024 112403 against 71573 (1.57x, control 154823 and 154818), fp32 N 2048 k 256 83688 against 56320 (1.49x), bf16 N 2048 k 256 19853 against 16528 (1.20x). Cells with one chunk per level (N 512 and 1024 at k 256, both types) did not move (7160 against 7095, 23262 against 22221). Files state/results/opt-W4/W4_wmerge_vs_W2_packed_w4_v2_wsort_*_20261025_165*.json (unrolled) and ..._v3_wsort_*_20261025_170*.json (rolled), source commits 6f4b9c2190 and 3146b39c03 on exp/topk-swarm/W4.
evidence: SASS instruction counts of the latency kernel (two inlined calls) from the batch JSON: bf16 N 2048 k 1024 21080 against 10216, fp32 N 2048 k 1024 39048 against 19320, fp32 N 2048 k 256 29144 against 18272, bf16 N 2048 k 256 15272 against 9400, with the same opcode mix per chunk (predicated LDS, VIMNMX or ISETP plus SEL exchanges, STS) and no STL or LDL in the fp32 kernels. The unrolled bf16 k 1024 kernel additionally carried a 200-byte stack frame with 53 STL and 51 LDL at 255 registers (the unroller kept several chunks' arrays live), the rolled one has no stack frame. 39048 instructions are about 620 KB of code for the two copies, the rolled kernel about 310 KB, both above any instruction cache level, but the per-call code of the rolled form (about 9.7k instructions) is what one call touches.
how to use: Roll any loop whose body is a complete network over a register array when the iterations are a dependent chain anyway (here the next chunk's load addresses need this chunk's win count, so unrolling buys no overlap): `#pragma unroll 1` on the chunk loop, the body indexed only by compile-time constants, the per-iteration offsets carried in a few registers. Read the SASS instruction count of the kernel from the batch JSON (`sass_instructions`) before reading cycles: a kernel whose count is several times a sibling cell's with the same opcode mix per unit of work is paying instruction fetch (as T48 found for a replicated cold refill), and the latency regime at one warp has no second warp to hide the fetch behind. Replace serial flag sums (`wins += flag`) on the critical path by a tree, it is free and takes 4 dependent adds instead of 16 off the chain.
caveats: One toolkit (13.4.92), one SM, one warp. The win is the fetch and the register pressure, not the algorithm: at 256 threads (W4_chunk4, one chunk per level) nothing changed. A rolled loop costs one branch and a few address registers per iteration (T49 measured about 10 cycles per rolled block for W2 rounds), which is below one percent of a 500-instruction body.
