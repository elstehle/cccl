### T?: a register array that escapes into a lambda or a non-unrolled loop lands in local memory with 0 spill bytes reported, check the stack frame and STL LDL counts
applies to: every fully unrolled register network or per-lane list (W1, N2, N5, W2 lists, B6 merge paths), any kernel that inlines a large primitive more than once (the harness latency kernel inlines the warm-up call and the chain call)
measured: W1_level fp32 N 256 k 64 (8 u64 words per lane, level-parallel bitonic top-k), harness latency chain-slope, GB200 sm_100, gb200-nvl4-ts2-99, nvcc 13.4.92, 2026-10-25: 14871 cycles per call with the word array in local memory against 3565 cycles with the same instruction stream in registers, the control W1_packed at 5291 in both sections. bf16 N 256 k 32: 15462 against 1657. Sub-warp LW 8 N 128 k 4 fp32: 17728 against 2337. Throughput was nearly unaffected (140.5 against 140.2 Gelem/s, the latency of the local loads hides behind 8 warps). Files state/results/opt-W1/W1_level_vs_W1_packed_focus_kill_n2_20261025_131737.json (local array) and W1_level_vs_W1_packed_focus_final3_20261025_134828.json (fixed).
evidence: ptxas -v for the latency kernel: `80 bytes stack frame, 0 bytes spill stores, 0 bytes spill loads`, `Used 70 registers, 80 bytes cumulative stack size`. cuobjdump -sass: STL 11 and LDL 11 in the latency kernel, 0 in the throughput kernel of the same TU (which inlines the network once and kept the array in registers). The first version indexed the array through a pointer offset inside `cuda::static_for` lambdas (`stage(k + tile * M, ...)`) and through `#pragma unroll` loops over the words. Passing the array by reference with a compile-time base index removed the local array in 4 of 12 warp cells, replacing every lambda and loop by template recursion removed it in all cells (approaches/W1/warp_level_topk.cuh). The remaining nonzero stack frames (bf16 LW 4 N 128 k 8 and 16) are honest 12-byte spills of the 64-register throughput kernel.
how to use: In a large fully unrolled network keep every array index a compile-time constant that the front end can see: template parameters through recursion, not lambda captures of the array (a lambda that is not inlined receives the array by address and the alloca escapes) and not `#pragma unroll` loops with array indexing in a function that already inlines thousands of instructions (the unroller can refuse and leave a dynamic index). Read `-Xptxas -v` for the stack frame line, not only the spill bytes: run.py records `stack_bytes`, `stl_count` and `ldl_count` per kernel in the batch JSON, the card schema and the summary tool show only spill bytes. A latency kernel can be hit while the throughput kernel of the same TU is clean, so check both kernels.
caveats: One toolkit (nvcc 13.4.92, aarch64 host). The exact inliner and unroller thresholds that trigger the escape are not known, the symptom is: array in `.local` with 0 spill bytes. The CUB WarpBitonicSortNetwork uses `static_for` with lambdas and pointer offsets without this problem at these sizes, its lambdas are small (one stage call) and the arrays are indexed by the caller's constants.
