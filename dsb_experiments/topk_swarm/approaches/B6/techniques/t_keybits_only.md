### T?: radix sort the key bits only with the index in the low bits of the word, the stable LSD sort orders ties by index, prefer_smaller_index costs nothing, bf16 needs 4 passes instead of 8 and the keys-only exchange beats the pairs sort by 1.24x
applies to: B6, the sorted-output pass (phase 3b), W4's sorted chunk runs, any radix sort of (key, index) whose input arrives in index order (blocked or striped tiles from the harness and from the batched agent), 16-bit keys in a 32-bit word above all, 32-bit keys in a 64-bit word where it ties the pairs sort
measured: cub::BlockRadixSort<uint32_t, 256, 8> on (twiddled bf16 key << 16 | index) with SortDescendingBlockedToStriped(words, 16, 32) against cub::BlockRadixSort<uint16_t, 256, 8, int> SortDescendingBlockedToStriped(keys, indices), same session, B200 umbriel-b200-020 sm_100, nvcc 13.4.92, 2026-10-25, harness latency chain slope, N 2048 k 1024 random: 5550 against 6878 cycles (1.24x), throughput 159 against 121 Gelem per s (1.31x), 56 against 64 registers, 26 against 29 BAR.SYNC. fp32 as (twiddled key << 32 | index) in a uint64_t sorted over bits 32 to 64 against the uint32_t key plus int value pairs sort: 13496 against 13398 (0.99x), 59.4 against 62.3 Gelem per s. prefer_smaller_index against not_guaranteed with the same binary: 5550.8 against 5550.5, the exact oracle passes on tie_heavy, signed_zero (after folding -0.0 onto +0.0), pivot_tie and all_equal. File state/results/opt-B6/B6_pairs_vs_B6_radix_b6_kill_pairs_20261025_155526.json, cards B6_pairs_b200_20261025_1 and B6_radix_b200_20261025_1.
evidence: cub::BlockRadixRank assigns ranks[i] = thread_prefix[i] + exclusive_digit_prefix with the thread prefix counted in item order and the digit prefix scanned in thread order, so the ranking is stable, and every pass of the LSD sort preserves the order of equal digits. The 32-bit word's exchange is one STS and one LDS per item per pass (96 STS, 47 LDS in the two-call kernel), the pairs sort adds a value exchange with its own barrier (29 against 26 BAR.SYNC). For the 64-bit word the SASS shows STS.64 and LDS.64 per item plus SHF.R.U64 for the digit, the same bytes through shared memory as key plus value.
how to use: Build the sort word as (order-preserving key image in the high bits, source index in the low bits), call the keys-only sort with begin_bit at the first key bit and end_bit at the top of the word, and read the index back from the low bits. Equal keys come out in ascending source index order because the input (blocked tile, item t x IPT + i) is in index order and the sort is stable, so the index bits are never sorted: 4 passes of 4 bits for bf16 and fp16, 8 for fp32. Fold -0.0 onto +0.0 before twiddling so both zeros are one tie class. For prefer_larger_index sort the inverted index bits as well (8 passes for bf16) or reverse the stable order.
caveats: Needs the input in index order (a striped tile is in index order within each item slot but not across slots: thread t item i is i x Threads + t, so stability gives index order per slot only, and the word then needs the index bits sorted too, or a blocked tile). A 32-bit word holds 16 key bits plus 16 index bits (N at most 65536). For 32-bit keys the 64-bit word has no advantage over the pairs sort at block scope (0.99x), unlike the warp scope where the u64 word is the route to the requirement (W1). The gain is relative to the pairs sort, the sort itself remains 2.2x behind the radix select at k = N/2 (the block sort cost entry).
