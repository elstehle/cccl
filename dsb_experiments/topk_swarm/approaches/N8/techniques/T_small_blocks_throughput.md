### T?: in the one-wave throughput regime 64-thread blocks give 1.2x to 1.66x over 256-thread blocks at the same threads per SM for a barrier-per-round primitive, and 1.2x to 1.5x for radix select at N up to 2048
applies to: B2 and every block primitive with a barrier per round (B5 block phase, B2_twolevel), radix select (B1_idx) and histogram primitives at N 1024 to 4096, the device agent's block size choice, both key types
measured: harness throughput regime (one occupancy wave, Gelem per s, same lock section), B2_packed at 64 against 256 threads: bf16 N 1024 1759 against 1289 (1.36x), 1325 against 843 (1.57x), 820 against 495 (1.66x), 443 against 273 (1.63x), 234 against 144 (1.62x) at k 4, 8, 16, 32, 64; N 2048 1.18x, 1.46x, 1.50x at k 8, 16, 32; N 4096 1.19x (k 16) and 1.25x (k 64); fp32 N 1024 1.20x to 1.56x, N 2048 0.83x to 1.30x (128 registers), N 4096 1.06x and 0.73x (254 registers). 128 threads sit between (bf16 N 1024 1.29x to 1.35x over 256). B1_idx at 64 against 256 threads: bf16 N 1024 k 16 601 against 409 (1.47x), N 2048 657 against 559 (1.18x), N 4096 566 against 692 (0.82x, 165 registers); fp32 N 1024 k 4 693 against 437 (1.59x). The same kernels lose in the latency regime: B2 at 64 threads is 0.83x to 0.97x of 128 threads at N 1024, B1_idx at 64 threads 0.54x of 256 threads. B200 sm_100, umbriel-b200-020, nvcc 13.4.92, 2026-10-25, card N8_b2packed_b200_20261025_1.json (B1_idx in the control column), batch state/results/opt-N8/N8_b2packed_vs_N8_b1idx_n8_b2t_20261025_145019.json.
evidence: occupancy from the batch (cudaOccupancyMaxActiveBlocksPerMultiprocessor): 32 blocks of 64 threads, 16 of 128, 8 of 256 per SM at bf16 N 1024, all 2048 threads per SM; the per-call work per block is the same at every block size (the harness loads the same N keys, the primitive does the same rounds); the 64-thread kernels have 0 spill and 32 registers (bf16 N 1024). Where the register tier drops the 64-thread occupancy (fp32 N 2048 at 128 registers, 8 blocks per SM) the gain disappears, which places the effect in the number of independent blocks per SM, not in the thread count.
how to use: When choosing a block size for a batched block primitive whose per-call cost is a chain of barriers (one per extraction round, two per radix pass), prefer the smallest block whose register tier still fills the SM: at N 1024 to 2048 that is 64 threads for B2 (32 blocks per SM, 1.4x to 1.66x) and for B1_idx (1.2x to 1.6x), at N 4096 64 to 128 threads for bf16 and 256 for fp32. A block of 2 warps waits at each barrier for one other warp and 32 such blocks interleave their rounds, a block of 8 warps idles 8 warps until its slowest arrives. The latency regime says the opposite (128 threads for B2, 256 for B1_idx), so a device agent that serves one row per block should take the throughput shape and a single-row primitive the latency shape.
caveats: One-wave throughput with the input reloaded from L1 or L2 per call, so the load phase is part of the per-call cost at every block size; a device kernel that loads each tile once from global memory has a different fixed cost per block and the gain is unmeasured there. Measured at N 1024 to 4096 with registers at most 80 for the 64-thread form; fp32 at IPT 32 and above (128 to 254 registers) and bf16 at N 4096 k 64 lose the edge. One node.
