# Techniques catalogue (append only)

Generally applicable optimizations, intrinsic costs and codegen lessons, one entry each, appended with `tools/append_locked.py`. Every number carries arch, CUDA version, node, date and the microbenchmark file. The knowledge curator folds entries into `TOPK_KNOWLEDGE_BASE.md` at every wave boundary. Entry ids are `T<n>`, assigned in order of appending.

Entry format:

```
### T<n>: <name>
applies to: <scopes, approaches, key widths>
measured: <number, arch, CUDA, node, date, file>
evidence: <SASS lines, file, or report section>
how to use: <one paragraph>
caveats: <where it does not hold>
author: <agent>
```

### T1: redux.sync.max.u32 costs about 22 cycles and compiles to one CREDUX
applies to: W2, B2 and B5 warp phases, any warp max or sum of 32-bit keys, all key widths once twiddled or packed into 32 bits
measured: redux.sync.max.u32 dependent chain B200 21.9, GB200 21.9 cycles per call. For comparison shfl_xor single B200 30.0, GB200 30.0, 5-shuffle max tree u32 B200 150.0, GB200 150.0, f32 (fmaxf) B200 150.0, GB200 150.0, u64 B200 189.8, GB200 189.8, ballot B200 26.7, GB200 26.7. B200 = NVIDIA B200 sm_100, umbriel-b200-020, nvcc 13.4.92, 2026-10-25. GB200 = NVIDIA GB200 sm_100, gb200-nvl4-ts2-92, nvcc 13.4.92, 2026-10-25. Chain-slope method of BRIEF section 4, min of 64 repetitions, file harness/micro/intrinsics_micro.cu, rows named as in the JSON under state/results/hw-researcher/<node>/.
evidence: `CREDUX.MAX UR5, R9` then `IMAD.U32 R9, RZ, RZ, UR5` (the result lands in a uniform register and is moved back), sass_sm_100.txt kernel `bench<ReduxU32, 4>`. The July 2026 numbers (22.4 redux, 30 shuffle, 150 and 190 trees) re-verified within one cycle on CUDA 13.4.92.
how to use: One redux replaces a 5-step shuffle tree (about 7 times cheaper) for any 32-bit integer reduction. The result is warp-uniform, so a following `lane == winner` test needs the per-lane value compared against it, see the W2 round entry.
caveats: Integer types only on the sm_100 baseline target. `.add` truncates to 32 bits. The uniform-register destination means the value is not in a per-lane register until the IMAD move, which the compiler inserts.
author: hw-researcher

### T2: redux.sync.max.f32 needs an sm_100f build and saves the twiddle round trip
applies to: W2 and B5 warp max of raw fp32 keys, threshold broadcasts, any fp32 warp reduction on B200, GB200, B300 and Rubin
measured: redux.sync.max.f32 B200 22.1, GB200 22.1 cycles, redux.sync.max.abs.NaN.f32 B200 22.1, GB200 22.1 cycles, both on the sm_100f build. GB200 = NVIDIA GB200 sm_100, gb200-nvl4-ts2-92, nvcc 13.4.92, 2026-10-25. Chain-slope method of BRIEF section 4, min of 64 repetitions, file harness/micro/intrinsics_micro.cu, rows named as in the JSON under state/results/hw-researcher/<node>/.
evidence: `CREDUX.MAX.F32 UR5, R6` and `CREDUX.MAXABS.F32.NAN UR5, R6` in sass_sm_100f.txt kernels `bench<ReduxF32, 4>` and `bench<ReduxF32AbsNaN, 4>`. The twiddled path is `SHF.R.S32.HI`, `LOP3.LUT`, `CREDUX.MAX`, `IMAD.U32`, `LEA.HI`, `LOP3.LUT` (sass_sm_100.txt, `bench<ReduxF32ViaTwiddle, 4>`). PTX ISA 9.4: `.f32` type requires sm_100a, supported on sm_100f from PTX ISA 8.8, nothing on plain sm_100.

Keep the twiddled u32 path as the sm_100 fallback and select at compile time on `__CUDA_ARCH_FAMILY_SPECIFIC__` (device pass) plus a host define for the launch.
caveats: The mandated swarm build (`-arch=sm_100`) cannot emit it, so an approach that relies on it reports an sm_100f variant next to the baseline. No CUDA C intrinsic exists, inline PTX only. 18 of the 40 cycles saved per round are the twiddle and untwiddle ALU work, so a design that keeps keys twiddled anyway gains nothing.

### T3: a W2 extraction round costs 89 cycles unpacked and 34 cycles with the index packed into the key
applies to: W2 redux based extraction at warp scope, B5 warp phases, keys of 16 bits or less (packed) and 32-bit keys (unpacked)
measured: unpacked round (redux max, ballot of `v == max`, ffs, winner select) B200 88.6, GB200 88.6 cycles. Packed round (redux max of `key << 16 | index`, winner by `v == max`) B200 35.5, GB200 35.5 cycles. Components: ballot + ffs + winner select alone B200 74.5, GB200 74.5, `__ffs` alone B200 40.0, GB200 40.0, redux alone B200 21.9, GB200 21.9. Warp max through 32 fire-and-forget shared atomics + syncwarp + LDS B200 48.6, GB200 48.6. B200 = NVIDIA B200 sm_100, umbriel-b200-020, nvcc 13.4.92, 2026-10-25. GB200 = NVIDIA GB200 sm_100, gb200-nvl4-ts2-92, nvcc 13.4.92, 2026-10-25. Chain-slope method of BRIEF section 4, min of 64 repetitions, file harness/micro/intrinsics_micro.cu, rows named as in the JSON under state/results/hw-researcher/<node>/.
evidence: unpacked kernel `bench<ReduxBallotRound, 4>`: `CREDUX.MAX`, `VOTE.ANY`, `BREV`, `FLO.U32.SH`, `ISETP` per round. Packed kernel `bench<ReduxPackedRound, 4>`: `CREDUX.MAX`, `ISETP`, `LOP3`, `SHF` per round (sass_sm_100.txt).
how to use: For keys of 16 bits or less, pack `(twiddled_key << 16) | (0xffff - index)` and every round is one redux plus a compare, 2.6 times cheaper than the unpacked round, deterministic and prefer-smaller-index for free. For 32-bit keys the ffs is the expensive part (BREV + FLO, about 40 cycles): resolve the winner with `__ballot_sync(v == m)` and `%lanemask_lt` based rank tests or a second redux of the lane id instead of `__ffs` when the critical path matters.
caveats: The packed form caps the index at 65535 per segment. At warp scope a redux round (22) beats the shared atomic round (49), the opposite of block scope where the atomic256 round wins (see the block max entry). The July figure of 82 cycles for the unpacked round is 89 here because this round includes the winner select.
author: hw-researcher

applies to: any lane election, rank or k-th candidate lookup on the critical path, all scopes
measured: dependent chains, cycles per call: `__ffs` B200 40.0, GB200 40.0, `__popc` (plus one IMAD) B200 22.8, GB200 22.8, `__fns(mask, 0, 2)` B200 176.6, GB200 176.6, `bmsk.clamp` + iadd B200 14.0, GB200 14.0 per op in the pair chain. B200 = NVIDIA B200 sm_100, umbriel-b200-020, nvcc 13.4.92, 2026-10-25. GB200 = NVIDIA GB200 sm_100, gb200-nvl4-ts2-92, nvcc 13.4.92, 2026-10-25. Chain-slope method of BRIEF section 4, min of 64 repetitions, file harness/micro/intrinsics_micro.cu, rows named as in the JSON under state/results/hw-researcher/<node>/.
evidence: `bench<FfsChain, 4>`: `BREV R0, R9` / `FLO.U32.SH R0, R0` / `IADD3` per call. `bench<FnsChain, 1>`: 43 instructions per call (`SHF`, `ISETP`, `POPC` x4, `SEL` x4, `SGXT` x4, `PRMT`), no FNS opcode exists in the Blackwell SASS table. `bench<BmskChain, 4>`: `BMSK R0, R0, 0x5` native (sass_sm_100.txt).
how to use: `__popc(ballot & lanemask_lt)` gives a rank in about 23 cycles and needs no FLO. `elect.sync` or a redux of the lane id are cheaper leaders than `__ffs` on a dependent path. author: hw-researcher

applies to: W3 digit histograms, duplicate detection and tie handling with `__match_any_sync`, warp scope
measured: cycles per call with U distinct values among 32 lanes: U=1 B200 51.4, GB200 51.4, 2 B200 61.9, GB200 61.9, 4 B200 83.9, GB200 83.9, 8 B200 127.9, GB200 127.9, 16 B200 215.9, GB200 215.9, 32 B200 391.9, GB200 391.9. B200 = NVIDIA B200 sm_100, umbriel-b200-020, nvcc 13.4.92, 2026-10-25. GB200 = NVIDIA GB200 sm_100, gb200-nvl4-ts2-92, nvcc 13.4.92, 2026-10-25. Chain-slope method of BRIEF section 4, min of 64 repetitions, file harness/micro/intrinsics_micro.cu, rows named as in the JSON under state/results/hw-researcher/<node>/.
evidence: `MATCH.ANY R6, R9` then `POPC R7, R6` per call, one SASS instruction whose latency grows with the number of distinct values (sass_sm_100.txt, `bench<MatchAnyClasses<32>, 4>`).

### T6: elect.sync is one SASS instruction whose latency hides behind a redux, no cheaper than ffs(activemask) but deterministic
applies to: the one-lane work after any warp reduction (shared memory write, atomic, counter), all scopes
measured: redux chain alone B200 21.9, GB200 21.9 cycles, redux chain with an `elect.sync` per step feeding the next input B200 29.0, GB200 29.0, the same with `__ffs(__activemask()) - 1` B200 29.3, GB200 29.3. The increment of about 6 cycles is the adds that consume the leader id, not the election. B200 = NVIDIA B200 sm_100, umbriel-b200-020, nvcc 13.4.92, 2026-10-25. GB200 = NVIDIA GB200 sm_100, gb200-nvl4-ts2-92, nvcc 13.4.92, 2026-10-25. Chain-slope method of BRIEF section 4, min of 64 repetitions, file harness/micro/intrinsics_micro.cu, rows named as in the JSON under state/results/hw-researcher/<node>/.
evidence: `ELECT P0, UR8, PT` (sass_sm_100.txt, `bench<ReduxElect, 4>`), the ffs variant is `VOTEU.ANY`, `UBREV`, `UFLO.U32.SH` on the uniform datapath (`bench<ReduxFfsLeader, 4>`).
how to use: `elect.sync` (inline PTX or `cuda::ptx::elect_sync`) is free when issued next to a reduction because it does not depend on the data, and it is deterministic (the same lane every time for the same mask), which `__activemask()` after divergence is not. author: hw-researcher

### T9: shared atomicMax with return costs 55 cycles uncontended and serializes at one lane per cycle on one address, u64 is a CAS loop
applies to: B2 atomics rounds, ticket counters, histogram bins in shared memory, block and warp scope

B200 = NVIDIA B200 sm_100, umbriel-b200-020, nvcc 13.4.92, 2026-10-25. GB200 = NVIDIA GB200 sm_100, gb200-nvl4-ts2-92, nvcc 13.4.92, 2026-10-25. Chain-slope method of BRIEF section 4, min of 64 repetitions, file harness/micro/intrinsics_micro.cu, rows named as in the JSON under state/results/hw-researcher/<node>/.
evidence: u32 is `ATOMS.MAX R0, [UR5], R0` (`bench<AtomUncontended<unsigned>, 1>`). u64 has no native shared max: `LDS.64`, `ISETP.LE.U32.AND`, `ISETP.LE.U32.AND.EX`, `@P0 BRA` (skip when not larger), `ATOMS.CAST.SPIN.64 P0, [R3], R8, R10`, `@!P0 BRA` retry loop with `BSSY` and `BSYNC` (`bench<AtomUncontended<unsigned long long>, 1>`, sass_sm_100.txt). caveats: Contention numbers are self-dependent chains per thread (every thread waits for its own return), the realistic round pattern is in the block max entry.
author: hw-researcher

### T10: fire-and-forget same-address shared atomics issue for free once per warp per round but serialize at 32 to 59 cycles when a warp repeats them back to back
applies to: B2 rounds (one atomic per thread per round), shared memory histograms (many atomics per thread), block scope
measured: pair chains with 8 fire-and-forget `atomicMax` per step interleaved with 8 dependent IMADs, against the IMAD base (B200 31.8, GB200 31.8 at 32 threads, B200 31.5, GB200 31.3 at 256): 1 lane on the slot and 31 on private words B200 31.5, GB200 31.5 (the atomics are hidden entirely), 32 lanes on one slot B200 446.1, GB200 446.1, 256 threads on one slot B200 2036.3, GB200 2028.1. Bursts of 8 independent atomics per step: 32 on one slot B200 475.6, GB200 475.6, 256 on one slot B200 2034.5, GB200 2037.0, 256 threads on 256 private words B200 71.9, GB200 71.5. One same-slot atomic per thread per round inside a block round: see the block max entry (74.5 cycles for the whole round including barrier and read back, 0 mismatches in the completion check). B200 = NVIDIA B200 sm_100, umbriel-b200-020, nvcc 13.4.92, 2026-10-25. GB200 = NVIDIA GB200 sm_100, gb200-nvl4-ts2-92, nvcc 13.4.92, 2026-10-25. Chain-slope method of BRIEF section 4, min of 64 repetitions, file harness/micro/intrinsics_micro.cu, rows named as in the JSON under state/results/hw-researcher/<node>/.
evidence: `ATOMS.MAX RZ, [R6], R7` (destination RZ, no return) with the address selected by `SEL`, no branch (`bench<AtomNoRet<unsigned, 256, 256>, 2>`, sass_sm_100.txt). Completion: `bench<BlockMaxAtomic256Check<unsigned>, N>` compares the slot read after `BAR.SYNC` with a shuffle tree max and counted 0 mismatches in 64 repetitions at every chain length on every node measured.
how to use: The B2 pattern (every thread one `atomicMax` into `slot[round]`, barrier, read) is cheap because the slot address is warp-uniform and ptxas aggregates the warp's 32 same-address fire-and-forget atomics into one `CREDUX.MAX` plus one atomic by an elected lane (T26 and T27 by opt-B2b, visible in `bench<BlockMaxAtomic256<unsigned>, 4>` as `CREDUX.MAX`, `VOTEU.ANY`, `UFLO`, `@P0 ATOMS.MAX RZ`), so eight atomics reach the shared memory unit per round and the read after the barrier is correct. Keep that address provably uniform (indexed by a round counter, never by per-thread data): the burst rows above select the address per thread, ptxas cannot aggregate them, and the hardware then serializes same-address lanes at about one per cycle (32 to 59 cycles per warp instruction). A shared memory histogram with data-dependent bins is in that regime, so pre-combine equal keys in registers or spread hits over banked copies, 256 threads over 256 private words issue at about 9 cycles per warp instruction.
caveats: The first version of this entry attributed the cheap round to merging inside the shared memory atomic unit, the SASS shows it is ptxas aggregation at compile time, which only happens for a provably uniform address without a returned value. The u64 fire-and-forget form is the CAS loop of the previous entry and skips the atomic when the value is not larger, so its burst number (B200 716.3) is not comparable.
author: hw-researcher
### T11: block-wide max round at 256 threads: atomic256 fire-and-forget 74 cycles, classic shuffle tree 290, hybrid with redux 149, u64 atomics 4500
applies to: B2 rounds, B5 merges, any block-wide max or argmax per round, 256 threads
measured: cycles per round: classic (warp shuffle tree, smem partials, barrier, 8-way shuffle) u32 B200 290.1, GB200 290.1, u64 B200 368.1, GB200 368.2, classic with redux for both phases B200 93.0, GB200 93.0, atomic256 (all threads fire-and-forget atomicMax into slot[n], barrier, read) u32 B200 74.4, GB200 74.5, u64 B200 4561.0, GB200 4531.5, atomic256 with return (each thread waits) then barrier B200 289.8, GB200 289.8, hybrid8 (shuffle tree, 8 lane-0 atomics) u32 B200 276.1, GB200 276.1, u64 B200 610.3, GB200 752.7, hybrid8 with redux B200 148.9, GB200 149.1. Components: `__syncthreads` at 128 B200 20.0, GB200 20.0, 256 B200 28.0, GB200 28.0, 512 threads B200 44.5, GB200 44.2, STS + LDS round trip B200 33.0, GB200 33.0. B200 = NVIDIA B200 sm_100, umbriel-b200-020, nvcc 13.4.92, 2026-10-25. GB200 = NVIDIA GB200 sm_100, gb200-nvl4-ts2-92, nvcc 13.4.92, 2026-10-25. Chain-slope method of BRIEF section 4, min of 64 repetitions, file harness/micro/intrinsics_micro.cu, rows named as in the JSON under state/results/hw-researcher/<node>/.
evidence: atomic256: `@P0 ATOMS.MAX RZ, [UR5+0x20], R6` / `BAR.SYNC.DEFER_BLOCKING 0x0` / `LDS R9, [UR5+0x20]` per round (sass_sm_100.txt, `bench<BlockMaxAtomic256<unsigned>, 4>`). The u64 round is the `ATOMS.CAST.SPIN.64` loop. Re-verifies the three July 2026 facts on CUDA 13.4.92: (1) the fire-and-forget u32 round costs about 74 cycles of which barrier (28) plus read back (32) are most, (2) the 64-bit packed word is dead at block scope (4500 per round, 368 even through shuffles), (3) pre-reducing with redux before the atomic makes the round slower (149 against 74) because ptxas already aggregates the uniform-address round into one `CREDUX.MAX` plus one elected atomic per warp (T26 and T27), so an explicit redux adds a second 22-cycle dependent step and the lane-0 atomic with a per-warp predicate is no longer aggregated the same way. New: the classic structure with redux for both phases (93) is the best non-atomic round, and the barrier scales 19, 28, 44 cycles at 128, 256, 512 threads.
how to use: For a block-wide max of 32-bit values use the atomic256 round. Reduce the value alone and resolve indices separately (ties are then resolved by a ticket or a second round), never pack value and index into 64 bits for shared atomics. how to use: Do not expect a per-item `if (match) atomicAdd` to predicate on long unrolled tiles, and do not reach for inline PTX to force it, ptxas undoes it. Guarded stores do predicate, so keep stores as plain `if (c) *p = v`. Avoid per-item generic pointers in such loops, they double the live registers.

Two warps per scheduler cost 92 per 8 redux each (16 per scheduler per step, 5.75 cycles per CREDUX), four warps per scheduler 165 per 8 (32 per scheduler, 5.2 per CREDUX). The same pattern holds for VOTE (16 per scheduler in 112 cycles, 7.0 each) and for SHFL at a higher rate (32 per scheduler in 127 cycles, 4.0 each, about one SHFL per cycle per SM).
how to use: Budget collectives per scheduler, not per SM: with W warps per scheduler each issuing C redux per round, the throughput floor of the round is about 5.5 W C cycles (7 W C for ballots, 4 W C for shuffles), and it only binds when that exceeds the latency chain of the round. At 256 threads (two warps per scheduler) two redux per warp per round cost 23 cycles of scheduler time, which hides inside a 74 to 93 cycle block round. A dependent redux chain at 21 cycles per step is unaffected by the other warps up to 16 warps per block. When a block round is slower than its latency model, look first for a collective whose latency landed on the critical path, not for a throughput limit. opt-B2b's SASS of the B2 spec3 round shows that ptxas moves a CREDUX across BAR.SYNC in both directions regardless of source order (the same redux sits before the STS in some rounds, between STS and barrier in others, and after the barrier before the LDS in others), and every placement after the barrier puts 22 cycles plus the UR to R move in front of the fold and the store. Source order is therefore not a tool for this, and at 256 threads the single aggregated CREDUX of the uniform-address atomic round (T10, T26, T27) is the floor.
caveats: One block per SM in the latency harness. With several resident blocks the per-scheduler budget is shared by all their warps. The per-scheduler versus per-SM distinction rests on the 4-warp row equalling the 1-warp row, which assumes the usual warp-to-scheduler assignment (warp id modulo 4).
